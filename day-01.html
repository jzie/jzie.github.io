Day 1, 17 September 2026

From zero to a car that answers back

Goal for the session: get a virtual Android Automotive vehicle running on my Mac, then read and write vehicle data myself instead of just watching the screen.

Phase
1 of 8: basics and the emulator
Tools
Android Studio, Android 15 automotive emulator, adb
Outcome
Read and wrote live vehicle speed

What I did, and why

  1. Installed Android Studio on an Apple Silicon MacBook.Why: It bundles the emulator, so the whole platform can be learned before buying any hardware.
  2. Downloaded the Android 15 automotive system image, Google APIs variant.Why: Android 15 is the newest stable automotive image, and the Google APIs build allows root access, which is what makes the layers below the app inspectable.
  3. Created a virtual vehicle and booted it.Why: It provides both a main screen and an instrument cluster, so I could see where vehicle values surface before writing any code.
  4. Simulated driving with the emulator's vehicle controls: gear to D, speed up.Why: To confirm the cluster reacts to vehicle data rather than being a static image, and to find where values enter the system.
  5. Read the live speed from the VHAL over adb.Why: Going straight to the vehicle data layer, beneath any app, shows what the platform actually holds and in which units.
  6. Wrote a speed into the VHAL from the terminal.Why: Writing from outside is the same direction my motorcycle's data will travel later, so it tests the path the real bridge will use.
  7. Decoded the property ID 0x11600207.Why: Each vehicle value carries an ID that encodes who defined it, what it covers and its type. My own motorcycle values will need IDs in the vendor range, so the scheme matters.

How the data flowed

The slider and my terminal commands both wrote into the VHAL. CarService passed each change on to the cluster app.

Evidence

Reading and writing vehicle speed

$ adb shell dumpsys \
    android.hardware.automotive.vehicle.IVehicle/default \
    --get PERF_VEHICLE_SPEED
VehiclePropValue{prop: 291504647, status: AVAILABLE,
  value: RawPropValues{floatValues: [39.166668]}}

39.17 metres per second, or 141 km/h, matching the slider.

$ adb shell dumpsys \
    android.hardware.automotive.vehicle.IVehicle/default \
    --set PERF_VEHICLE_SPEED -f 25

The cluster jumped to 56: 25 m/s is 90 km/h, shown in mph.

What the ID 0x11600207 means

DigitsMeaning
1Defined by Google, a standard value
1Applies to the whole vehicle
60Stored as a decimal number
0207Which value: vehicle speed

My own motorcycle values will start with 2, meaning defined by me rather than Google.

What I learned

Apps never touch the hardware

Values flow through the VHAL and CarService, which enforce permissions and update rates. Motorcycle data has to enter at the VHAL, not be patched into the app.

Store in one unit, show in another

The VHAL holds speed in metres per second, while the cluster showed miles per hour because the emulator is set up as a US vehicle. Data and presentation are separate concerns.

The last writer wins

When the slider and the terminal both sent a speed, the VHAL kept whichever came last, and the slider never noticed. On the bike, exactly one source must own each value, or the screen can show a wrong number without warning.

IDs are a contract

A property ID packs who defined it, what it applies to, its data type and what it is. Designing those IDs for RPM, gear and coolant temperature is one of my next deliverables.
