Android Automotive motorcycle cluster

Product decisions

Every decision I make on this project, with the options I considered, why I chose one and what I gave up. Grouped by session, newest first.

Day 2, 18 September 2026

From the session My own app, reading the vehicle.

Frame this as a manufacturer-style feasibility POC

Decided
Options considered
A personal HUD gadget; a feasibility study of the question a motorcycle manufacturer would actually ask
Choice
Feasibility POC: can Android Automotive run a motorcycle instrument cluster, and where does the boundary sit?
Why
The interesting question is not whether a screen can show numbers. It is whether Android can own the rider-facing cluster while a separate layer owns the legally required warning lights, which is how the industry handles the fact that Android Automotive holds no automotive safety certification.
Trade-off
A much higher bar: the POC has to speak to start-up time, the safety split and cost, not just a working screen.

Design for a single display

Decided
Options considered
Follow the car model of a main screen plus a cluster; treat the one screen as the whole cluster
Choice
One display, one full-screen app
Why
A motorcycle has an instrument cluster and nothing else, and the Raspberry Pi will drive a single display. Android Automotive's cluster APIs assume a second screen exists, so using them here would add system-level complexity for no gain.
Trade-off
I set aside the platform's own cluster APIs for now, and will revisit them when the POC covers the safety split.

No interaction while riding

Decided
Options considered
A touch interface like a car's; a display with no interaction at all in motion
Choice
Zero interaction while moving, and the app starts by itself at power-on
Why
With gloves, one small screen and no passenger, anything that needs a tap is a distraction and a safety problem. There is also nobody to launch an app on a bike.
Trade-off
Every setting has to be handled while parked or from another device.

A custom layout, not Google's Car App Library

Decided
Options considered
Car App Library templates; Media service template; a plain activity with my own layout
Choice
A plain activity with my own layout
Why
The Car App Library gives driver-distraction checks for free but only allows its own fixed screens: lists, grids and navigation. A cluster is a few very large numbers, which those templates cannot express.
Trade-off
I own the driver-distraction responsibility that the templates would have enforced.

Minimum Android version 33

Decided
Options considered
API 28, which covers 95% of phones; API 33
Choice
API 33
Why
Phone install-base percentages are irrelevant here: this app runs on one emulator and one Raspberry Pi, both Android 15. A lower floor would only add compatibility work for vehicle versions I will never target.
Trade-off
Older Android Automotive versions are ruled out, which is fine for a POC but would need revisiting for a production fleet.

Subscribe to vehicle values instead of polling

Decided
Options considered
Ask for values on a timer; register a callback and let the platform push changes
Choice
A callback registered with CarService, at its on-change rate
Why
Pushed updates arrive as fast as the vehicle produces them and cost less power than polling, and the platform also delivers the current value the moment you subscribe, so the display is populated at power-on rather than blank.
Trade-off
Silence looks identical to a steady value, so the app needs its own staleness check before it can be trusted on the bike.

A second bike with no data bus

Planned
Options considered
One bike only; add a 1985 Yamaha XS 650 as a second target
Choice
Add the older bike as a second target after the R3
Why
If a 40-year-old bike with no electronics and a modern connected bike both feed the same set of vehicle values, that demonstrates the platform layer is independent of the vehicle and only the bridge changes: a useful finding for any manufacturer with a mixed range.
Trade-off
Extra hardware and sensor work, so it stays out of scope until the R3 prototype runs.

Day 1, 17 September 2026

From the session From zero to a car that answers back.

Build on Android Automotive, not a plain phone app

Decided
Options considered
A regular Android app on an old phone; Android Automotive OS
Choice
Android Automotive OS
Why
Learning the platform is the goal, and a prototype running on it proves that learning.
Trade-off
A steeper learning curve and more setup than a phone app.

Learn on Android 15

Decided
Options considered
Android 17, the newest phone release; Android 15 automotive
Choice
Android 15
Why
It's the newest stable automotive emulator image, and most guides and examples match it.
Trade-off
Newer Android 17 features come later, with some differences to handle when I move up.

Use the Google APIs emulator image

Decided
Options considered
Google Play image; Google APIs image
Choice
Google APIs image
Why
It allows root access, so I can inspect vehicle data directly, and it lets me test my own driving-safe screens.
Trade-off
No Play Store inside the emulator.

Raspberry Pi for the display

Planned, to confirm in Phase 6
Options considered
An old Android phone; Raspberry Pi
Choice
Raspberry Pi
Why
Community Android Automotive builds exist for it, while old phones rarely can run it.
Trade-off
It needs its own power supply, mounting and weatherproofing.

One focused step per session

Decided
Options considered
Large sessions covering several steps; one verified step at a time
Choice
One step per session, each with a clear done check
Why
An hour a day is sustainable, and checking each step before moving on keeps problems small.
Trade-off
A longer overall timeline of roughly five to six months.

Build in public

Decided
Options considered
Share only the finished prototype; publish progress as I go
Choice
A public portfolio with session notes and this decision log
Why
It shows how I think and decide, not just the end result, and it keeps me accountable.
Trade-off
Mistakes and dead ends are visible too.
