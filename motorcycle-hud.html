Why a product manager is doing this

I've worked on connected-vehicle products at the system level. Building one end to end teaches the constraints that shape a roadmap: what the platform gives you for free, where data can go wrong, and what it takes to keep a rider safe. Those are the conversations I want to have with engineering teams from real experience, not slides.

How a value reaches the screen

In Android Automotive, apps never read vehicle hardware directly. Every value passes through two platform layers first. Today the input is a slider in the emulator. Later it will be my bike.

Session 1: from zero to a car that answers back

17 September 2026

  1. Installed Android Studio on an Apple Silicon MacBook.
  2. Downloaded the Android 15 automotive system image and created a virtual car.
  3. Simulated driving: set the gear to D and raised the speed with the emulator's car controls. The instrument cluster followed.
  4. Read the live speed straight from the VHAL using adb, Android's command-line debugging tool.
  5. Wrote a speed into the VHAL from the terminal and watched the cluster change without touching the slider.
  6. Decoded the property ID to see how Android labels each piece of vehicle data.

Reading and writing vehicle speed

$ adb shell dumpsys \
    android.hardware.automotive.vehicle.IVehicle/default \
    --get PERF_VEHICLE_SPEED
VehiclePropValue{prop: 291504647, status: AVAILABLE,
  value: RawPropValues{floatValues: [39.166668]}}

39.17 metres per second, or 141 km/h, matching the slider.

$ adb shell dumpsys \
    android.hardware.automotive.vehicle.IVehicle/default \
    --set PERF_VEHICLE_SPEED -f 25

The cluster jumped to 56: 25 m/s is 90 km/h, shown in mph.

What the ID 0x11600207 means

DigitsMeaning
1Defined by Google, a standard value
1Applies to the whole vehicle
60Stored as a decimal number
0207Which value: vehicle speed

My own bike values will start with 2, meaning defined by me rather than Google.

What I learned

Apps never touch the hardware

Values flow through the VHAL and CarService, which enforce permissions and update rates. For my display, bike data has to enter at the VHAL, not be patched into the app.

Store in one unit, show in another

The VHAL holds speed in metres per second, while the cluster showed miles per hour because the emulator is set up as a US car. Data and presentation are separate concerns.

The last writer wins

When the slider and the terminal both sent a speed, the VHAL kept whichever came last, and the slider never noticed. On the bike, exactly one source must own each value, or the screen can show a wrong number without warning.

IDs are a contract

A property ID packs who defined it, what it applies to, its data type and what it is. Designing those IDs for RPM, gear and coolant temperature is one of my next deliverables.

Safety rules I've set

  • Read-only on the bike. The bridge only listens to the motorcycle's data and never sends anything onto it.
  • Glanceable, not distracting. No animations, notifications or dense text while riding.
  • Check before mounting. Road rules for displays, helmet approval and warranty impact get checked before anything goes on the bike.
